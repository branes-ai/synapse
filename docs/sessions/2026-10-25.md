## #48: mmproj image encoders (issue #45)

`models/clip.hpp` loads the vision tower from a llama.cpp mmproj file: a SigLIP
ViT, then a pixel shuffle, then a linear projection to the text model's width.
The graph gained `layer_norm`, `gelu`, `add_rows`, `self_attention` and
`pixel_shuffle`, plus a row divisor on tensors (invariant I9: a graph with a
pixel shuffle accepts only full runs). Tiny random-weight idefics3 fixtures
match llama.cpp to 1.3e-5 (F32) and 1.1e-7 (Q8_0) RMS. Opt-in, the real
SmolVLM-256M F16 and Q8_0 files match to 1.7e-3 and 4.8e-2 RMS.

## #51: register-blocked quantized gemm (issue #50)

Batched quantized products run in 4-row × 2-token register tiles. Integer
block sums stay exact in vector lanes, so tiling does not change results
(G1, D1). `session::parallel` now hands out several pieces per thread that
threads take as they finish, so E-cores and hyperthreads no longer hold up the
team.

## #55: gelu by table lookup (issue #52)

GELU had been 0.76 s of every encode, at any thread count. It now reads
`ggml_gelu_f32` from a 65536-entry table indexed by binary16, built once in
static storage. The output is still bit-identical to ggml, and GELU now takes
20 ms per encode on one thread.

## #57: register-tiled self-attention (issue #53), this session

### Design

- `self_attention_keys` transposes each head's K into scratch:
  `head_dim` rows, each `self_attention_key_stride(n)` long (n padded to a
  whole number of vectors, padding zeroed).
- A score tile is 6 queries × 2 key vectors: it broadcasts `q[t][c]`, loads
  `kt[c][j..]`, and fmas. The old kernel did one horizontal `reduce_dot` per
  score; the new one does none.
- The weighted sum is 6 queries × 2 output vectors per loaded V row. A scalar
  `scalar_fma` tail covers a `head_dim` that the vector width does not divide.
- **D1 by construction.** Every score is one fma chain over d, and every
  output element one over j, whatever the tile shape. A row's result
  therefore does not depend on the query split. The test splits the queries
  at 10 and 11 to cut the tiles differently and compares bit for bit. The
  checksum was identical across every tile shape tried.
- **`kernels::softmax` is faster with bit-identical output.** It takes the max
  a vector at a time (exact in any order), then runs the exp pass and the
  in-order double sum as separate loops, so the sum's latency chain no longer
  stalls the exps. The decode paths share this softmax; Llama-3.2-1B still
  matches its golden.
- **Work split:** `self_attention_query_blocks` went from 4 to 16, with blocks
  rounded up to whole query tiles. The K transposes run as their own parallel
  pass over heads. The scratch is now the transposed K for every head plus
  one score slot per unit, with overflow checks in `graph_builder`.

### Verification

- ctest, 151/151 in each build: gcc-release-hwy, gcc-release (scalar
  backend), gcc-debug, clang-release, clang-debug, asan.
- Opt-in real-model tests: `clip_model` with SmolVLM-256M f16 and Q8_0 (gcc
  AVX2 and ASan), and `llama_model` with Llama-3.2-1B.
- CI: the first push failed on MSVC (C4459, a template loop variable `d`
  shadowing a test's global `d`, the same thing #51 hit) and on
  clang-format. Both were fixed in a follow-up commit; then CI went green,
  CodeRabbit found nothing actionable, and the PR was squash-merged as
  `98b68a4`.

### Pitfalls hit

- A scratch benchmark built with `-march=x86-64-v3` but without
  `-maes -mpclmul` silently gets Highway's SSE4 target: 4 lanes, and mul + add
  instead of fma. The first numbers of the session were taken that way and
  had to be redone.
- MTL5's thread pool is sized from `MTL5_NUM_THREADS` on first use. Without
  it, a `session{g, 20}` in a standalone program runs on one thread.
- gcc's `-Waggressive-loop-optimizations` fired, under `-Werror`, on a
  scalar tail loop written as `for (; e < head_dim; ++e)` after the vector
  loops. Restarting the loop from `head_dim / w * w` silenced it.

## Open threads

- Softmax is now the largest attention phase, about 45% of the phase total
  (~0.31 of ~0.65 s). Most of it is scalar `std::exp`, about a third of the
  kernel's 0.67 s (~0.22 s). A vector exp needs bit-cast and shift on float lanes, which
  `mtl::simd::batch` does not offer yet. Filed upstream as
  [stillwater-sc/mtl5#654](https://github.com/stillwater-sc/mtl5/issues/654).
