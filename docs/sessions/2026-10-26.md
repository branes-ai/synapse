CodeRabbit posted two findings on #59. Both were correct:

### Process lesson: the review check is not the review

The findings were picked up late, and only because the user asked about them.
The PR had been reported ready on the strength of
`gh pr checks`, where the CodeRabbit row read "pass — Review completed". That
check only means CodeRabbit finished; its findings are separate review
comments. From #61 on, every PR watch also fetches:

- `gh api repos/<owner>/<repo>/pulls/<n>/reviews`
- `gh api repos/<owner>/<repo>/pulls/<n>/comments` (inline)
- unresolved review threads, via GraphQL `reviewThreads { isResolved }`

`/complete-pr` checks for zero unresolved threads before merging.

## stillwater-sc/mtl5#654: vectorized exp

[stillwater-sc/mtl5#654](https://github.com/stillwater-sc/mtl5/issues/654),
labelled `enhancement` and `feature` in the style of mtl5#628. There was no
existing exp issue, and MTL5 v5.20.0's `batch` still had no exp, no
float/int32 bit-cast, no integer shift, no float-to-int rounding, and no
lane-wise min or max.

- **Evidence:** #57's phase timings. 151 M exponentials take ~0.22 s,
  ~1.5 ns each. The softmax is shared by the LLM decode paths too.
- **Proposal:** `batch<T> exp(batch<T>)` and a version over a whole array.
  It should document its ULP bound and special-value behaviour, give the same
  result for an input whatever lane it is in, and use the same algorithm in
  the scalar backend. Exposing the bit-cast, shift, round and min/max
  primitives instead is the fallback option.
- **No claimed speedup:** the issue says only that a vector exp "could
  plausibly cut that by several times", since nothing was measured.

were checked, including review comments, before the merge as `fa6fc97`.
